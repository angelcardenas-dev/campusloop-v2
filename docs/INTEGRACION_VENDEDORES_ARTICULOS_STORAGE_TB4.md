# Integración de vendedores, artículos y fotografías privadas TB4

Base de trabajo local: commit de perfiles `c9943e6`, publicado en el PR #79 hacia `integracion/bernabe`. Los cambios se conservan en una rama separada del PR de perfiles. Las seis migraciones aplicadas quedan intactas.

## Operaciones disponibles localmente

- **Vendedores.** La migración `20261125000200` incluye solicitud idempotente, historial propio, cola de pendientes, aprobación y rechazo por revisor habilitado y notificación interna. Exige cuenta confirmada, perfil completo y versión vigente de normas. El plazo es de 48 horas corridas y la cola ordena por vencimiento. El vencimiento conserva el estado pendiente. La decisión bloquea la autorización del revisor, el perfil y la solicitud. La aprobación activa al vendedor e incrementa la versión del perfil en la misma transacción que registra la decisión y la notificación. La revisión del expediente propio queda denegada. Las tablas privadas de revisores y normas se inicializan vacías.
- **Artículos.** La migración `20261125000300` añade edición de título, descripción, categoría, condición y precio del artículo disponible propio, y retiro lógico del artículo propio. Conserva el tipo físico `BIGINT`, moneda PEN y precio positivo. La entrada JavaScript acepta enteros seguros. La RPC bloquea la fila, exige versión esperada y deniega operaciones sobre una reserva activa. La RPC futura de reservas debe usar el mismo bloqueo antes de validar disponibilidad y rechazar artículos retirados. El catálogo conserva la consulta GET existente. La migración `20261125000500` añade alta idempotente de vendedores activos, valida campus y categoría activos y reclama en la misma transacción una foto del titular registrada en la tabla privada de verificaciones. Guarda los metadatos acreditados, bucket y ruta. Las nuevas filas dejan `imagen_url` nula.
- **Storage.** La migración `20261125000400` requiere el bucket privado `articulos` ya configurado por API administrativa con JPEG/PNG/WebP y 2 MiB. Las políticas autorizan subida de una ruta propia por vendedor activo y firma o descarga autenticada de una referencia ligada a un artículo visible. La subida inicial queda sin acceso de lectura hasta su vinculación. La API cliente carece de listado general, sobrescritura y borrado del bucket. El resolver JavaScript pide una firma de 60 segundos y valida origen, ruta y parámetro de firma. La política de firma no impone un TTL máximo al cliente directo.
- **Servicios.** `js/operaciones-tb4.js` expone las llamadas de vendedores, edición y retiro de artículos, y el resolver de fotos por ID. Reutiliza el SDK compartido y conserva la respuesta `{ ok, datos, error }`. Netlify incluye el módulo. El controlador de vendedores puede usar `consultarEstadoVendedor` para el estado normalizado. El contrato de alta devuelve el DTO esperado por Publicaciones, incluidas fechas, versión, estado y la referencia privada. El controlador de Matías permanece intacto y requiere inyección de `crearMiArticulo` con la clave estable del intento. El catálogo presenta firmas mediante la dependencia opcional `resolverFotoPrivada` y usa una tarjeta sin foto en caso de ausencia o denegación. El GET no incluye firmas en sus DTO.

## Dependencias del corte

1. **Vendedores.** Coordinación debe publicar la versión de normas que se aceptará, designar revisores y definir cobertura y escalamiento humano. Matías consumirá el historial y la solicitud en los estados de sus pantallas. La interfaz de revisión y la campana deben conectarse con sus responsables.
2. **Alta y sustitución de fotografías.** En la base aplicada, `imagen_url` sigue siendo obligatoria. El alta local cambia su nulabilidad y el GET local admite ambos formatos. El corte requiere publicar primero los adaptadores compatibles de Explorar/Inicio y conectar el flujo de Matías. Antes de registrar una fila en `tb4_ventas_privado.fotos_verificadas`, un componente servidor autorizado debe comprobar propietario, ruta, existencia, bytes, formato real y dimensiones. Esa integración todavía no está conectada. La API cliente no puede crear ni alterar evidencias de verificación.
3. **Retención y limpieza.** La subida y el alta de un artículo son operaciones separadas. Definir la idempotencia de alta y un estado de objeto reclamado o excluido que serialice vinculación y limpieza. Un operador autorizado puede borrar mediante la API solo tras descartar referencias, incluidas las retiradas sujetas a retención. El navegador mantiene DELETE cerrado. Una URL firmada ya emitida conserva su vigencia aunque el artículo se retire. Si se exige un máximo de vigencia aplicado por el servidor, cerrar la firma directa y coordinar un firmador con TTL fijo o descarga autenticada.
4. **Compatibilidad vigente.** Esta rama conserva la URL pública y sus consumidores para las filas existentes. El alta está preparada localmente. El reemplazo de foto y la limpieza de huérfanos quedan pendientes de coordinar retención y la exclusión mutua entre vinculación y borrado.

## Prueba y despliegue previsto

En PostgreSQL desechable, instalar las seis migraciones, las dos migraciones de negocio, el [simulador de Storage](../tests/db/preparar_storage_articulos_tb4.sql), las migraciones de políticas y de alta, y la [prueba integrada](../tests/db/vendedores_articulos_tb4.sql). Ejecutar también `node --experimental-vm-modules --test tests/operaciones/operaciones-tb4.test.mjs` y `node scripts/preparar-netlify.mjs`.

La validación local pasó en PostgreSQL 18 con Auth y Storage simulados. Dos revisores concurrentes produjeron una decisión, una notificación y un conflicto `PT409`. También pasó la retención de historial tras cancelar una reserva y retirar el artículo. La prueba SQL verificó además que el alta rechaza fotos sin evidencia, que un reintento idéntico devuelve el mismo artículo y que un reintento alterado devuelve conflicto. Las suites JavaScript específicas y el build incluyeron el contrato privado y sus regresiones públicas.

Antes de una aplicación autorizada, verificar que la base de integración contenga perfiles, inventariar políticas y permisos de Storage, comprobar versión y nombres de sus operaciones, y ensayar en una instancia Supabase aislada con cuentas sintéticas. Crear o conciliar el bucket por el canal administrativo de Storage antes de aplicar su migración. Si la integración de fotos se despliega después, publicar las migraciones de vendedores y edición por separado del corte. El dry-run debe mostrar únicamente las versiones autorizadas para esa entrega. No se aplicaron estas migraciones a CampusLoop.

## Decisiones para una sola revisión de coordinación

| Decisión | Propuesta para ratificar |
| --- | --- |
| Normas | Publicar texto y versión inmutable antes del alta de solicitudes. Activar la versión desde administración y conservar el historial de aceptaciones. |
| Revisores | Designar cuentas existentes por UUID mediante un canal administrativo auditado. Mantener la matriz de habilitación fuera del cliente y asignar cobertura y escalamiento de las 48 horas. |
| Verificación de fotos | Autorizar un componente servidor con identidad propia y permisos acotados. Debe recuperar el objeto exacto, comprobar propietario y ruta, decodificar los bytes con límites de tamaño y dimensiones, y registrar la evidencia solo si el objeto sigue siendo el verificado. La ACL del navegador queda cerrada para esa tabla. |
| Vigencia de firmas | Si 60 segundos debe ser un máximo exigible, quitar las operaciones de firma directa del navegador y usar un firmador autorizado con TTL fijo, o descarga autenticada bajo RLS sin enlace portador. |
| Reemplazo | Subir y verificar una ruta inmutable nueva. Cambiar la referencia con versión esperada y reclamar la evidencia en una transacción. Conservar la referencia anterior para retención hasta la decisión administrativa de limpieza. |
| Huérfanos | Acordar ventana de retención y proceso recuperable. Serializar la exclusión de una ruta para limpieza con el alta o reemplazo, comprobar referencias históricas y borrar bytes únicamente por la API de Storage. |

La autorización de revisión, la identidad de vendedor, las escrituras acotadas y el bloqueo de sobrescritura desde el navegador están implementados localmente. El control sobre el contenido binario real y la vigencia máxima de las firmas dependen de los componentes anteriores. La política vincula el objeto a un artículo visible por bucket, ruta y propietario. Una firma emitida sigue siendo utilizable durante su vigencia.
